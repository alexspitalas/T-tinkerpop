= Temporal Functionality

== Overview

Apache TinkerPop™ has been extended with temporal functionality, enabling time-aware graph queries and traversals. This extension provides:

1. **Lifetime Management**: Define and update one or more validity intervals for vertices and edges, and assign lifetimes to vertex properties
2. **Allen's Interval Algebra**: Thirteen operators for interval-based temporal filtering
3. **Temporal Paths**: Constrain traversals based on temporal relationships between edges
4. **Temporal Views**: Query a graph at an instant or during a window
5. **Temporal PageRank**: Rank vertices using a chronological edge stream

== Lifetime Management

=== Setting Lifetimes

The `lifetime()` step allows you to define or replace the temporal validity of graph elements. Its one-argument
form has an open-ended end. `lifetimeProperty()` assigns a lifetime to a vertex property.

[source,java]
----
// Vertex with start and end time
g.addV("employee")
  .lifetime("2020-01-15T09:00:00", "2023-12-31T17:00:00")
  .property("name", "Alice")
  .next();

g.addV("employee")
  .lifetime("2020-01-01")
  .property("name", "Bob")
  .next();

// Edge whose lifetime is contained in both endpoint lifetimes
g.V().has("name", "Alice").as("a")
  .V().has("name", "Bob").as("b")
  .addE("manages")
  .from("a").to("b")
  .lifetime("2022-06-01T09:00:00", "2023-12-31T17:00:00")
  .next();

// A vertex property with its own lifetime
g.V().has("name", "Alice")
  .lifetimeProperty("title", "manager", "2022-06-01", "2023-12-31")
  .iterate();
----

=== Retrieving Lifetime Information

[source,java]
----
Vertex employee = g.V().has("name", "Alice").next();
Date startTime = g.V(employee).getStartTime().next();
Date endTime = g.V(employee).getEndTime().next();
Lifetime lifetime = g.V(employee).getLifetime().next();
List<Lifetime.Interval> intervals = lifetime.getIntervals();
----

The getter steps work on vertices, edges, and vertex properties. `getStartTime()` and `getEndTime()` return
`java.util.Date` values; for multiple intervals they return the earliest start and latest end.

=== Internal Representation

Lifetimes are stored as properties:

- `startTime`: Earliest start of validity (missing or `null` = unbounded start)
- `endTime`: Latest end of validity (missing or `null` = open-ended end)
- `temporalIntervals`: Normalized intervals as comma-separated `start:end` epoch-millisecond pairs

When Gremlin represents an element as a `Lifetime`, missing temporal properties are normalized to unbounded interval
limits. An element with no lifetime properties is therefore treated as always valid by temporal view helpers
and other steps that read `Lifetime` values. The `getEndTime()` step uses the same normalized open-ended behavior and
returns the maximum representable end time when no end bound is stored. When `temporalIntervals` is
present, it is authoritative; the two outer-bound properties do not represent gaps between intervals. An edge
lifetime must be contained in the lifetimes of both endpoint vertices when it is set or changed.

=== Adding and Dropping Intervals

`addInterval(start, end)` adds an inclusive interval; `dropInterval(start, end)` subtracts one. Overlapping or
touching intervals are merged. A subtraction may split an interval, with the retained sides ending one millisecond
before and beginning one millisecond after the removed interval. `lifetime(start, end)` replaces all intervals.
On an element without explicit lifetime properties, `addInterval()` establishes the first bounded interval.
These interval mutation steps operate on vertices and edges; use `lifetimeProperty()` to assign a vertex-property lifetime.

[source,java]
----
Vertex contract = g.addV("contract")
    .lifetime("2020-01-01", "2030-12-31").next();
g.V(contract).dropInterval("2024-01-01", "2024-12-31").iterate();
g.V(contract).addInterval("2032-01-01", "2032-12-31").iterate();
List<Lifetime.Interval> activePeriods = g.V(contract).getLifetime().next().getIntervals();
----

The default `Lifetime.DropMode.SOFT` rejects a drop that leaves no intervals.
`dropInterval(start, end, Lifetime.DropMode.HARD)` removes the element when its entire lifetime is subtracted.
Removing a vertex also removes its incident edges. A drop that misses all intervals leaves the lifetime unchanged.

=== Temporal Views

`atTime(instant)` filters elements alive at one instant; `window(start, end)` filters elements whose lifetime
intersects the inclusive window. Both carry the temporal scope through later vertex, edge, and vertex-property
navigation, including `out()`, `outE()`, `inV()`, `has()`, `values()`, and `properties()`.

[source,java]
----
List<Vertex> currentEmployees = g.V().hasLabel("employee")
    .atTime("2022-07-01").toList();
List<Vertex> reports = g.V(employee)
    .window("2022-01-01", "2022-12-31")
    .out("manages").toList();
----

An `atTime(t)` query uses the point interval `[t, t]`. When navigating from a temporal vertex, the edge and both
endpoints must each intersect the current temporal context. In a window query these intersections need not occur
at one shared instant. A direct `g.E().atTime(...)` or `g.E().window(...)` filters the edge by its own lifetime.
Both steps reject `null` arguments, and `window()` rejects a reversed range.

== Allen's Interval Algebra

=== Overview

Allen's Interval Algebra provides 13 distinct temporal relationships between intervals, extended with a general `intersects` operator. These operators can be used in two ways:
1. **As standard traversal steps**: Comparing the current element against a static reference element (e.g., `temporalOverlaps(ref)`).
2. **As Cypher-style binary predicates**: Using `TemporalP` inside `where()`, `has()`, or `match()` steps to dynamically compare graph variables (e.g., `where("a", TemporalP.overlaps("b"))`).

These temporal filters are fully **multi-interval aware**. When evaluating elements with fragmented lifetimes (i.e., multiple active periods separated by gaps), the filters perform a full O(N+M) temporal sweep to ensure mathematically correct overlap and subset logic. For instance, an element is only considered `during` a reference if all of its active sub-intervals are perfectly enclosed by active sub-intervals of the reference, without falling into any gaps.

=== Using Temporal Predicates (Pattern Matching)

The `TemporalP` predicate wrapper unlocks dynamic binary pattern matching, allowing you to declare temporal relationships between traversal variables:

[source,java]
----
// Find all cases where a fraud investigation completely contained 
// a series of suspicious transfers, but the account was closed 
// immediately after the transfers finished.
g.V().match(
    __.as("acc").outE("investigation").as("i"),
    __.as("acc").outE("transfer").as("t"),
    __.as("acc").outE("closed").as("c")
).where("t", TemporalP.during("i"))
 .where("c", TemporalP.metBy("t"));

// Find an edge that overlaps with the temporal bounds of a specific event
g.E().hasLabel("event").as("event")
 .V().outE("active").where(TemporalP.intersects("event"));
----

=== The 13 Allen Operators

[width="100%",cols="2,5,3",options="header"]
|===
|Operator |Description |Example Use Case

|`temporalPrecedes(ref)`
|Element ends before reference starts
|Tasks before a deadline

|`temporalSucceeds(ref)`
|Element starts after reference ends
|Events after a milestone

|`temporalMeets(ref)`
|Element ends exactly when reference starts
|Perfect handoffs

|`temporalMetBy(ref)`
|Element starts exactly when reference ends
|Sequential processes

|`temporalOverlaps(ref)`
|Element starts before reference, both overlap
|Overlapping meetings

|`temporalOverlappedBy(ref)`
|Reference starts before element, both overlap
|Overlapping shifts

|`temporalDuring(ref)`
|Element fully contained within reference
|Subtasks within project

|`temporalContains(ref)`
|Element fully contains reference
|Projects containing tasks

|`temporalStarts(ref)`
|Both start together, element finishes first
|Sprint tasks starting together

|`temporalStartedBy(ref)`
|Both start together, reference finishes first
|Main task with early subtask

|`temporalFinishes(ref)`
|Both finish together, element starts later
|Tasks converging to deadline

|`temporalFinishedBy(ref)`
|Both finish together, reference starts later
|Project with late-joining task

|`temporalEquals(ref)`
|Identical start and end times
|Exactly matching intervals
|===

=== Usage Examples

[source,java]
----
// Find all tasks that must complete BEFORE a milestone
Vertex milestone = g.V().has("type", "milestone").has("name", "Release 1.0").next();
List<Vertex> priorTasks = g.V().hasLabel("Task")
    .temporalBefore(milestone)
    .toList();

// Find events that occurred DURING a specific time period
Vertex maintenanceWindow = g.V().has("type", "maintenance").next();
List<Vertex> incidents = g.V().hasLabel("Incident")
    .temporalDuring(maintenanceWindow)
    .toList();

// Find other meetings whose lifetimes intersect a particular meeting, including containment and shared boundaries
Vertex meeting = g.V().hasLabel("Meeting").next();
Lifetime meetingLifetime = Lifetime.fromProperties(meeting);
List<Vertex> conflicts = g.V().hasLabel("Meeting")
    .hasId(P.neq(meeting.id()))
    .filter(t -> Lifetime.fromProperties(t.get()).intersects(meetingLifetime))
    .toList();

// Complex temporal queries with where()
Vertex projectVertex = g.V().has("name", "Project Alpha").next();
List<Vertex> complexQuery = g.V().hasLabel("Task")
    .where(__.or(
        __.temporalDuring(projectVertex),
        __.temporalOverlaps(projectVertex)
    ))
    .toList();
----

== Temporal Paths

=== Overview

Temporal paths extend standard graph traversals by enforcing temporal constraints across edges in a path. This enables queries like "find paths where all edges overlap" or "find paths that respect causality."
Each path step follows an outgoing edge and returns its incoming vertex. It accepts zero or more edge labels;
without labels it considers all outgoing edges. Intervals that meet at a single instant count as overlapping.

=== Three Path Types

[width="100%",cols="2,5,3",options="header"]
|===
|Type |Constraint |Use Case

|`continuousPath(labels...)`
|All edges must overlap at a common time point
|Concurrent collaborations, team activities

|`sequentialPath(labels...)`
|Each edge starts ≥ when previous ends (causality)
|Workflows, event sequences, dependencies

|`pairwiseContinuousPath(labels...)`
|Consecutive edges overlap
|Hand-off processes, relay activities
|===

`sequentialPath(minDelay, maxDelay, labels...)` also limits the delay between the preceding edge's end and
the next edge's start, inclusive, in milliseconds. `pairwiseContinuousPath(true, labels...)` also requires
each new edge to start no earlier than the preceding edge; the default form has no monotonicity constraint.
Continuous and pairwise paths intersect the actual intervals of multi-interval edge lifetimes, including gaps.
Sequential paths use each edge lifetime's earliest start and latest end.

=== Continuous Paths

All edges in the path must share at least one common time point.

[source,java]
----
// Find 4-person teams where all worked together simultaneously
List<Path> teams = g.V().has("name", "Alice")
    .continuousPath("collaborates")
    .continuousPath("collaborates")
    .continuousPath("collaborates")
    .path()
    .toList();

// Timeline visualization:
// Edge 1: [10:00-12:00]
// Edge 2:   [11:00-13:00]
// Edge 3:     [11:30-12:30]
// Edge 4:       [12:00-14:00]
// Common overlap: [12:00-12:00] ✓ Valid continuous path
----

=== Sequential Paths

Each edge must start at or after the previous edge ends, ensuring temporal causality.

[source,java]
----
// Find causal process chains
List<Vertex> workflow = g.V().has("status", "started")
    .sequentialPath("processedBy")
    .sequentialPath("processedBy")
    .sequentialPath("processedBy")
    .has("status", "completed")
    .toList();

// Timeline visualization:
// Edge 1: [10:00-11:00] ends
// Edge 2:      [11:00-12:00] starts when Edge 1 ends
// Edge 3:           [12:00-13:00] starts when Edge 2 ends
// Perfect sequential handoffs ✓
----

=== Pairwise Continuous Paths

Adjacent edges must overlap, but not necessarily all edges simultaneously.

[source,java]
----
// Find hand-off chains where consecutive steps overlap
List<Vertex> handoffs = g.V().has("type", "task")
    .pairwiseContinuousPath("handedTo")
    .pairwiseContinuousPath("handedTo")
    .pairwiseContinuousPath("handedTo")
    .toList();

// Timeline visualization:
// Edge 1: [10:00-12:00]
// Edge 2:   [11:00-13:00] overlaps with Edge 1 ✓
// Edge 3:       [12:30-14:00] overlaps with Edge 2 ✓
// Edge 4:         [13:30-15:00] overlaps with Edge 3 ✓
// Note: Edge 1 and Edge 4 don't overlap - that's OK for pairwise
----

=== Branching Paths

When a vertex has multiple outgoing edges, temporal path filters evaluate each independently and return ALL valid paths.

[source,java]
----
// Graph structure: A->B->{C, D, E}
// Timeline:
//   A->B: [10:00-12:00]
//   B->C: [11:00-11:30] (overlaps A->B) ✓
//   B->D: [11:30-12:00] (overlaps A->B) ✓
//   B->E: [12:30-13:00] (no overlap) ✗

List<String> results = g.V(vertexA)
    .continuousPath("follows")
    .continuousPath("follows")
    .values("name")
    .toList();
// Returns: ["C", "D"] - both valid paths, E filtered out
----

=== Using with Repeat

Temporal paths integrate with `repeat()` for dynamic exploration.

[source,java]
----
// Find all continuous paths up to depth 5
List<Path> allPaths = g.V().has("name", "start")
    .repeat(__.continuousPath("connected"))
    .times(5)
    .path()
    .toList();

// Find paths until reaching a specific target
List<Vertex> targetPaths = g.V().has("name", "source")
    .repeat(__.sequentialPath("flows"))
    .until(__.has("name", "destination"))
    .toList();

// Combine with emit() for all intermediate results
List<Vertex> allNodes = g.V().has("id", 1)
    .repeat(__.pairwiseContinuousPath("knows"))
    .emit()
    .times(3)
    .toList();
----

=== Temporal Paths with Shortest Path

You can combine temporal constraints with shortest path algorithms.

[source,java]
----
// Find one sequential path (the first returned path is not necessarily shortest)
List<Path> oneSequentialPath = g.V().has("name", "start")
    .repeat(
        __.sequentialPath("edge")
          .simplePath()
    )
    .until(__.has("name", "end"))
    .limit(1)
    .path()
    .toList();

// Alternative: Find all paths then select shortest
List<Path> allSequentialPaths = g.V().has("name", "start")
    .repeat(__.sequentialPath("edge").simplePath())
    .until(__.has("name", "end"))
    .path()
    .toList();

Path shortest = allSequentialPaths.stream()
    .min(Comparator.comparingInt(Path::size))
    .orElse(null);

// Continuous shortest path: collect candidates before comparing their lengths
List<Path> allContinuousPaths = g.V().has("name", "start")
    .repeat(
        __.continuousPath("collaborates")
          .simplePath()
    )
    .until(__.has("name", "end"))
    .path()
    .toList();
Path shortestContinuous = allContinuousPaths.stream()
    .min(Comparator.comparingInt(Path::size))
    .orElse(null);
----

== Implementation Notes

=== Performance Considerations

1. **Indexing**: Available indices depend on the graph provider; outer-bound properties alone do not describe gaps in a multi-interval lifetime
2. **Edge Properties**: Temporal path filters use `Lifetime` normalization, so an edge with no lifetime properties
   has unbounded interval limits
3. **Path Length**: Longer paths with continuous constraints require more intersection calculations

=== Time Format

The implementation uses `java.util.Date` values. `Lifetime` accepts `Date`, `Instant`, epoch milliseconds as a
`Number`, and parseable date strings. String forms include `2023-06-15`, `2023-06-15T14:30:00`, and
`2023-06-15T14:30:00Z`. The `lifetime()`, `addInterval()`, and `dropInterval()` traversal methods expose string
and child-traversal overloads; `atTime()` and `window()` accept the supported temporal values directly.

=== Null Handling

- An absent `startTime` is treated as an unbounded start when represented as a `Lifetime`
- An absent `endTime` is treated as an open-ended end when represented as a `Lifetime`
- Elements with no lifetime properties are treated as always valid by temporal view helpers
- When neither `startTime` nor `temporalIntervals` is present, `getStartTime()` returns the date represented by `Lifetime.MIN_START_TIME`
- When neither `endTime` nor `temporalIntervals` is present, `getEndTime()` returns the date represented by `Lifetime.MAX_END_TIME`

== Advanced Examples

=== Combining Allen Operators with Temporal Paths

[source,java]
----
// Find sequential paths whose reached vertices are DURING a project timeframe
Vertex project = g.V().has("name", "Project Alpha").next();

List<Path> constrainedPaths = g.V().has("type", "task")
    .repeat(
        __.sequentialPath("depends")
          .temporalDuring(project)
    )
    .times(3)
    .path()
    .toList();
----

=== Multi-Constraint Queries

[source,java]
----
// Find continuous collaboration paths that:
// 1. All overlap (continuous)
// 2. Have edges DURING Q1 2023
// 3. Involve at least 4 people

Vertex q1_2023 = g.addV("timeframe")
    .lifetime("2023-01-01T00:00:00", "2023-03-31T23:59:59")
    .next();

List<Path> results = g.V()
    .hasLabel("person")
    .repeat(__.continuousPath("collaborates"))
    .times(3)
    .path()
    .filter(__.unfold()
        .hasLabel("collaborates")
        .temporalDuring(q1_2023)
        .count().is(P.gte(3))
    )
    .toList();
----

== Temporal PageRank

`temporalPageRank()` performs a chronological edge-stream scan on the vertices arriving at the step. It considers
outgoing edges whose endpoints are both in that vertex set, writes a rank property to each selected vertex, and
passes the incoming vertex traversers onward. Walk mass arriving across an edge becomes available when that edge
ends; this is different from the iterative static `pageRank()` algorithm.

[source,java]
----
List<Vertex> ranked = g.V().hasLabel("person")
    .temporalPageRank()
    .with(TemporalPageRank.propertyName, "temporalRank")
    .with(TemporalPageRank.alpha, 0.85d)
    .with(TemporalPageRank.beta, 0.5d)
    .with(TemporalPageRank.normalize, true)
    .toList();
----

The defaults are `alpha = 0.85`, `beta = 0.5`, normalization enabled, and property name
`gremlin.temporalPageRank.pageRank`. `alpha` must be greater than zero and less than one; `beta` must be greater
than zero and at most one. Vertices with no eligible edges receive rank `0.0`. For a multi-interval edge, the
scan uses its earliest start and latest end.

== Summary

The temporal extensions to Apache TinkerPop provide a framework for time-aware graph analysis, while opening the way for more:

- **Lifetime Management** makes temporal validity a first-class property
- **Allen's Operators** enable sophisticated interval-based queries
- **Temporal Paths** allow traversals that respect temporal constraints
- **Temporal Views** filter later navigation at an instant or within a window
- **Temporal PageRank** ranks vertices using temporal edge order

For more examples and test cases, see:
- `TemporalPathIntegrationTest.java` - Comprehensive temporal path tests
- `AllenTemporalIntegrationTest.java` - Allen operator test coverage
- `AtTimeIntegrationTest.java` and `WindowIntegrationTest.java` - Temporal view tests
- `MultipleIntervalLifetimeIntegrationTest.java` - Multi-interval mutation tests
